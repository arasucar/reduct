# Reduct planning agents

An agent started in this directory is a planning and documentation agent. Follow the application's parent instructions. Read the compact `agent/README.md` for roles, boundaries, record access, and edits. Retrieve detailed procedures with `reduct guide TOPIC` or `agent/reference/README.md` when needed: `mapping` for first setup, `planning-procedure` for review and handoff, and `completion` for planned implementation and completion.

Resolve requests by stable record ID, Markdown path, or title. Use `list` to locate records and `context ID --compact` to identify required reading. Read the target, applicable parent constraints, linked features, supporting evidence, and open reviews; batch required reads with `read-many --format text`. Reuse exact content already read in this session only after checking its hash. For staged workspaces use `source_repository` to find the application. Reconcile changed content before edits and report record paths, unresolved decisions, and evidence limits. Use section or exact-passage patches for local changes. Read the guide's deeper procedures only when performing those operations.

## Document formatting

Keep new and revised product documents simple and easy to comment on. Use plain paragraphs, ATX headings (`#`, `##`, `###`), flat bullet or numbered lists, occasional bold emphasis, single-line inline code, and ordinary Markdown links. Use LF line endings and spaces instead of tabs. Keep inline formatting within one line.

Prefer prose and short lists. Avoid blockquotes, nested lists, tables, task checkboxes, HTML, images, diagrams, and decorative formatting. If a code example is necessary, use a fenced block starting at column one, with spaces for indentation; keep it outside lists and blockquotes. Keep source references in a separate section.

Preserve required record headings, YAML frontmatter, stable IDs, and evidence. Apply these conventions to current drafts; do not reformat retained versions, rewrite discussion history, or alter exact owner quotations. See `reduct guide formatting` or Document formatting in `agent/reference/README.md` for the shared convention.

For comments, do the requested work and use `review resolve` with one informative answer explaining the result or rationale. This posts the answer and marks the thread addressed; no separate reply or resolution summary is needed. Use `review reply` only when feedback still needs work or an answer from the owner.

Create Works directly under a Module. Link affected Features within or across Modules; Features are not Work parents. Missing or incomplete Feature documentation does not block starting a Work. Create or update Feature records as behavior is delivered, and link newly documented Features to the Work before completion.

Planning should converge toward a concrete implementation. Record owner answers under Decisions and remove the questions they settle. Ask new owner questions only when the answer materially changes scope or essential behavior, protects data, or avoids a costly commitment. Separate Implementation blockers from Investigation notes, Agent choices, and Testing observations. State exactly which scope a blocker prevents; proceed with independent agreed scope while unrelated questions remain open. Use `needs_owner_decision` only when the next concrete change is blocked; keep `in_progress` when independent implementation continues.

Choose routine technical details and reasonable defaults within the authorized scope. Keep investigation evidence under Investigation notes and record chosen implementation defaults under Agent choices; changes to those defaults must update the handoff instructions. Existing combined Investigation and agent choices sections remain part of drift checks. Do not require every interaction or edge case to be settled before implementation. Reversible details, such as an extreme-width toolbar fallback, belong in Testing observations: implement the agreed layout with a reasonable default, let the owner test it, and refine it through targeted adjustments. Follow the loop: initial implementation → owner testing → feedback → targeted adjustments.

Keep shared decisions in one canonical Work or Analysis record and reference its stable ID and section from related Works. A copied implementation brief must still include the applicable settled instructions so it can be executed independently. Prepare the brief for the agreed scope that can proceed, explicitly excluding blocked scope; unrelated open questions do not prevent handoff. Source drift calls for reconciliation of changed instructions, not restarting planning or reopening settled decisions.
